# IBM Langflow OSS: auto-login and code-validation chain (CVE-2026-9198)

An unauthenticated caller can obtain a privileged token from affected IBM Langflow OSS and use code validation to execute Python. Upgrade to remove both stages of that chain from the exposed service.

**Result.** The marked request reached the backend in the baseline and raised its counter. The native rule refused that request with HTTP 403 and preserved HTTP 200 for the benign probe. The synthetic fixture ran through Eden 1.103.0 on November 12, 2026 (UTC).

## The vulnerability

The advisory describes two stages in IBM Langflow OSS. The auto-login route can issue a privileged token to an unauthenticated caller. A subsequent request can use the code-validation handler to execute Python. The token issuance and code execution are distinct steps.

IBM lists 1.0.0 through 1.10.0 as affected and 1.10.1 as fixed. The CVE record reports a CVSS base score of **9.8**.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies requests to `/api/v1/validate` and its descendants. The empty method list leaves the deny unrestricted by HTTP method. This is a coarse rule and blocked the benign probe on the same path.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/api/v1/validate",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** `gabriel_ibmlangflow_v1` waits for the request to be complete, checks whether the request target starts with `/api/v1/validate/code`, and looks for any configured marker in the body. The substring comparison is ASCII case-insensitive. Outside that prefix or without a marker, the module returns `Continue`. The shown lines are excerpts from the linked source.

```rust
const ROUTE: &[u8] = b"/api/v1/validate/code";
static NEEDLES: [&[u8]; 3] = [b"auto_login", b"token_bypass", b"exec("];
```

```rust
NEEDLES.iter().any(|n| find_ignore_case(body, n).is_some()) && return Ok(Decision::Refuse);
```

## Implement the remediation

Use this procedure in an isolated fixture to reproduce the scoped restriction. Follow the vendor update for the underlying exposure. See [deployment prerequisites](../deployment.md).

1. **Prepare the target.** Verify the loaded product and version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source when applicable.
2. **Apply the declarative policy.** Scope the policy to `/api/v1/validate` and descendants (all methods, `deny`). Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Run an authenticated `GET /api/v1/interlays/{interlay}` with `X-Eden-Verbose: true`. Save its complete current settings object as `current-settings.json` and retain the prior remediation declaration for recovery. Set `IDEMPOTENCY_KEY` to a fresh key for this intended mutation.

Save the JSON in the patch section as `remediation.json`.

```sh
jq -e --slurpfile policy remediation.json \
  '.remediation = $policy[0] | {settings: .}' current-settings.json \
  > interlay-update.json
eden api request PATCH "/api/v1/interlays/$INTERLAY" \
  --header "Idempotency-Key:$IDEMPOTENCY_KEY" \
  --body-file interlay-update.json --content-type application/json --confirm
```

3. **Verify the serving policy.** Read back the interlay.

```sh
eden api request GET "/api/v1/interlays/$INTERLAY" \
  --header 'X-Eden-Verbose:true'
```

Check that `remediation_status.state` is `ready` and both desired and effective SHA-256 values match the intended declaration. Replay the benign and marked requests in the recorded comparison on an isolated target. Check the recorded response and backend outcome for each probe.
4. **Restore the previous policy.** Coordinate the change with any other operator updating this interlay. Read current settings again and merge the saved remediation field into them. If the prior settings had no remediation field, omit it in the replacement. Send the same PATCH with a fresh idempotency key, then read back the intended state. Repeat the verification probes. Keep the affected route isolated if restoring the prior settings reopens exposure.

**Vendor update.** Use the [advisory](https://www.ibm.com/support/pages/node/7278927) to select the fixed release for the installed branch. Reported fixed releases include `1.10.1`. Follow the vendor’s update instructions and confirm the version actually loaded by the service.

## Fixture and probes

The fixture was a synthetic HTTP handler behind Eden. It answered the probes and kept a separate counter that increased when the handler recognized its marker bytes. The counter measures a fixture effect. An HTTP 200 from the baseline does not by itself establish that the counter moved.

**Request.** `POST /api/v1/validate/code` for the benign probe and the marked probe.

The benign probe carried an ordinary validation value. The second contained an execution marker and an auto-login field in the same validation request. The fixture recorded the marked body when forwarded.

## Signed module authority

The module import returned HTTP 201 and required explicit activation. Signature verification was deferred at import. Read-only inspection returned HTTP 403, admission with a tampered statement returned HTTP 400, and admission with an invalid signature returned HTTP 403. The activation receipt reported the module serving on all expected shards.

After revocation, the same marked request received HTTP 503. Re-approval and reactivation restored HTTP 403. The source digest below identifies the linked Rust file. The binary digest identifies the artifact recorded in the activation evidence.

## Test scope

The module examines only the validation route prefix. It has no state connecting two requests and does not stop token issuance at auto-login. The observed refusal applies to the marked validation request. It leaves the full two-request chain and validation payloads without the listed markers unverified.
