# ASUS router: root command execution via cross-site induced requests (CVE-2026-88711)

Certain ASUS router firmware models run injected OS commands as root when a logged-in administrator is induced to visit a malicious website that submits a state-changing request to the router's HTTP interface. The durable repair is the fixed firmware release.

## The vulnerability

The advisory describes OS command injection reachable by inducing a logged-in administrator to visit a malicious website — a cross-site POST to the router's admin interface carrying the injected field. Eden can front the router's HTTP interface, so the induced request rides an HTTP request Eden can refuse before the firmware's handler ever sees it.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the recorded route family and its descendants. This is a coarse rule: it also blocked the benign probe on the same route, which is the recorded false positive.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [
            "POST"
          ],
          "path": "/",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** asus_router_cross_site_command_injection_guard waits for a complete request and refuses POST requests whose Origin header host does not match the request's Host header host — the cross-site induced POST that the advisory documents as the exploitation precondition. Same-origin admin UI posts (matching Origin) and scripted administration (no Origin header) pass unchanged. The injection endpoint and parameter are not published, so the module gates the precondition rather than a parameter signature; this is stated as partial.

```rust
if !request_line.starts_with(b"POST ") { return Ok(Decision::Continue); } // then: Origin host != Host host -> Refuse
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-88711/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded ASUS router firmware version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission.
2. **Apply the declarative policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged.
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the advisory-shaped request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** The fixed release carries the durable repair; the [advisory](https://cve.now/CVE-2026-88711) links the vendor's update instructions where available. Eden's tiers are an enforcement stopgap for a deployment that cannot upgrade immediately.

## Fixture and probes

The benign probes submitted a scripted administration POST with no Origin header (curl-style tooling) and a browser-shaped same-origin POST whose Origin matched the router's Host. The advisory-shaped probe submitted a cross-site POST (Origin: a malicious site, Host: the router) carrying a shell-metacharacter command in the form field. The fixture mirrored the router's primitive: it marked the trigger when a cross-origin POST carried the injected command.

## Measured comparison (2026-11-18 UTC)

The values after each status are the observed increases in the fixture's effect counter.

| Probe | Baseline | Declarative policy | Native module |
| --- | --- | --- | --- |
| benign scripted (no Origin) | 200, +0 | 403, +0 | 200, +0 |
| benign same-origin UI post | 200, +0 | 403, +0 | 200, +0 |
| attack cross-site injection | 200, +1 | 403, +0 | 403, +0 |

Finite lab route, and the rule is stated as partial: the vendor has not published the injection endpoint or parameter, so the module gates the documented cross-site precondition for every POST on the fronted interface rather than a CVE-specific parameter signature. A same-origin compromise of the admin browser or a scripted request without an Origin header is out of scope; the tier-1 rule (deny every POST) is the coarse fallback.
