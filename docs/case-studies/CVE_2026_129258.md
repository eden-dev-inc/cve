# Tenda AC18: unverified firmware install via the upgrade handler (CVE-2026-129258)

Tenda AC18 devices accept a caller-supplied upgradeFile through /cgi-bin/upgrade without sufficient verification of data authenticity, letting a high-privilege network caller install crafted firmware — full and persistent control of the router.

## The vulnerability

The upgrade handler applies a caller-supplied firmware image without verifying its authenticity, so a crafted image becomes the device's operating software. Eden fronts the router's admin interface, so the crafted upgrade rides an HTTP request Eden can refuse before release.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the recorded fixture route and its descendants. This is a coarse rule: it also blocked the benign probe on the same route, which is the recorded false positive.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/cgi-bin/upgrade",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** gabriel_tenda_v1 waits for a complete request, matches the upgrade handler by path, and refuses any request carrying an upgradeFile parameter — the unverified-install shape the handler accepts. Requests without an upgrade file continue.

```rust
const ROUTE: &[u8] = b"/cgi-bin/upgrade";
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-129258/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded Tenda AC18 version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source.
2. **Apply the declaratory policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged. Full command sequences are in the [API example](../../cve/CVE-2026-129258/http-request-filter/api.md).
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the advisory-shaped request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** The fixed release carries the durable repair; the [advisory](https://cve.now/CVE-2026-129258) links the vendor's update instructions where available. Eden's tiers are an enforcement stopgap for a deployment that cannot upgrade immediately.

## Fixture and probes

The benign probe requested an upgrade check. The advisory-shaped probe supplied an upgradeFile through the same handler. The fixture incremented its marker when an unverified firmware upload reached the handler.

## Measured comparison (2026-11-14 UTC)

The values after each status are the observed increases in the fixture's effect counter.

| Probe | Baseline | Declarative policy | Native module |
| --- | --- | --- | --- |
| Benign upgrade check | 200, 0 | 403, 0 | 200, 0 |
| Advisory-shaped unverified firmware | 200, 1 | 403, 0 | 403, 0 |

The rule refuses upgradeFile-bearing requests on the upgrade route wholesale — a deliberate posture for a router's firmware surface, since no caller-supplied image is verifiable at the boundary. The real-world path is a high-privilege login. The durable fix is the vendor's signature verification.

## Signed module authority

Read-only inspection was refused (403) for the reader principal, admission of a tampered statement was rejected (400), and admission of an invalid signature was refused (403).
