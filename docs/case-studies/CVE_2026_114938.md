# Java4Shell: memory corruption in the OpenJDK Base64 decoder (CVE-2026-114938)

An unauthenticated remote caller can submit malformed Base64 data to an affected OpenJDK runtime, overwrite neighboring heap memory, disclose it, and reach remote code execution. Update OpenJDK to remove the vulnerable optimized decode path.

## The vulnerability

OpenJDK decodes Base64 with a hand-rolled x86-64 intrinsic that uses AVX-512 VBMI instructions on supported processors. The intrinsic computes the final store mask from the input and output lengths and adjusts it for padding. For a 65-byte input (`A`×64 + `=`), the decoder allocates a 50-byte result array; the padded-tail arithmetic underflows the output length to a negative value, which passes unchanged through the `bzhiq` mask trim, leaving the full 64-bit mask set. The following `evmovdqub` then writes 64 bytes starting near the end of the buffer — 62 bytes past it (offsets 50–111 in the vendor's standalone trigger). Java rejects the input afterwards, but by then neighboring heap objects may already be corrupted. On OpenJDK 17 the threshold is higher and the documented trigger is `A`×128 + `=` (129 bytes, offsets 50–159).

The same malformed tail family triggers with `=`, `==`, `X=`, `X==`, `XY=`, or `===` as the final 64-aligned chunk: any Base64 value **at least 64 bytes long whose length is 1, 2, or 3 modulo 64 and that ends with `=`**. The publisher demonstrated pre-auth remote code execution in default configurations of Keycloak, Atlassian Jira, Atlassian Confluence, JFrog Artifactory, Jenkins, and PingFederate, and post-auth chains in Apache Kafka Broker, Apache Solr, Elasticsearch, Gerrit, and Netflix Spinnaker, plus sample applications on Apache Struts and Spring Boot. The weaponized per-product chains are withheld by the publisher until the fixed releases are deployed.

The corruption requires an x86-64 processor with AVX-512 VBMI (Intel Ice Lake or newer; AMD Zen 4 or newer; Emerald Rapids — the verification CPU — is in that set). The vendor's standalone trigger prints `REPRODUCED` on an affected JDK and hardware combination.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies requests to `/api/decode` and its descendants. The empty method list leaves the deny unrestricted by HTTP method. This is a coarse rule: it blocked the benign decode probes on the same path.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/api/decode",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** `gabriel_j4s_v1` waits for the request to be complete, checks whether the request target starts with `/api/decode`, and scans the body and the request head for a maximal Base64-alphabet run at least 64 bytes long whose length is 1, 2, or 3 modulo 64 and that ends with `=` — the padded-tail underflow family, including both documented triggers (65 and 129 bytes) and the `==`/`===` variants. Valid Base64 values are always a multiple of 4 long, so their length modulo 64 is never 1, 2, or 3: the module cannot match a decodable value, and every refusal is an input the decoder would reject anyway. Outside the route or without a trigger shape, the module returns `Continue`. This is the complete rule, from the linked source:

```rust
const ROUTE: &[u8] = b"/api/decode";

fn is_b64_alphabet(b: u8) -> bool {
    (b >= b'A' && b <= b'Z') || (b >= b'a' && b <= b'z') || (b >= b'0' && b <= b'9')
        || b == b'+' || b == b'/' || b == b'='
}

/// True when the bytes contain a maximal Base64-alphabet run whose length `L >= 64`
/// satisfies `L % 64` in 1..=3 and ends with `=`: the documented padded-tail
/// underflow family. Valid Base64 values are a multiple of 4 long, so their
/// remainder modulo 64 is never 1, 2, or 3 and they never match.
fn has_underflow_tail(bytes: &[u8]) -> bool {
    let n = bytes.len();
    let mut i = 0usize;
    while i < n {
        if !is_b64_alphabet(bytes[i]) {
            i += 1;
            continue;
        }
        let start = i;
        while i < n && is_b64_alphabet(bytes[i]) {
            i += 1;
        }
        let len = i - start;
        if len >= 64 {
            let tail = len % 64;
            if (tail == 1 || tail == 2 || tail == 3) && bytes[i - 1] == b'=' {
                return true;
            }
        }
    }
    false
}
```

In `evaluate`, after the completeness wait and the route check, the module scans both surfaces where the trigger can ride the request — the body (upload and message fields) and the head (`Authorization: Basic` credentials) — and returns `Refuse` on the first match:

```rust
let target = &request_line[path_at + 1..];
if !target.starts_with(ROUTE) { return Ok(Decision::Continue); }
// ... body_range / body resolution ...
if has_underflow_tail(body) { return Ok(Decision::Refuse); }
if has_underflow_tail(head) { return Ok(Decision::Refuse); }  // Authorization: Basic
Ok(Decision::Continue)
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md).

1. **Prepare the target.** Verify the loaded product and version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source when applicable.
2. **Apply the declarative policy.** Scope the policy to `/api/decode` and descendants (all methods, `deny`). Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Run an authenticated `GET /api/v1/interlays/{interlay}` with `X-Eden-Verbose: true`. Save its complete current settings object as `current-settings.json` and retain the prior remediation declaration for recovery. Set `IDEMPOTENCY_KEY` to a fresh key for this intended mutation.

Save the JSON in the patch section as `remediation.json`.

```sh
jq -e --slurpfile policy remediation.json \
  '.remediation = $policy[0] | {settings: .}' current-settings.json \
  > interlay-update.json
eden api request PATCH "/api/v1/interlays/$INTERLAY" \
  --header "Idempotency-Key:$IDEMPOTENCY_KEY" \
  --body-file interlay-update.json --content-type application/json --confirm
```

3. **Verify the serving policy.** Read back the interlay. Check that `remediation_status.state` is `ready` and both desired and effective SHA-256 values match the intended declaration. Replay the benign and marked requests in the recorded comparison on an isolated target.
4. **Restore the previous policy.** Coordinate the change with any other operator updating this interlay. Read current settings again and merge the saved remediation field into them. If the prior settings had no remediation field, omit it in the replacement. Send the same PATCH with a fresh idempotency key, then read back the intended state.

### Native module `gabriel_j4s_v1`

1. **Prepare the archive.** Use the linked source and a compatible Eden SDK. Obtain the built archive and manifest from a qualified Eden build environment. Configure independent host approval for the installed Eden release. Use the authenticated principals required by the native authority contract. Set `PATCH_ARCHIVE` to the exact schema-2 package and `PACKAGE_SHA256` to its expected archive digest. Verify and import it using the same target interlay.

```sh
printf '%s  %s\n' "$PACKAGE_SHA256" "$PATCH_ARCHIVE" | sha256sum --check &&
  eden api request PUT "/api/v1/interlays/$INTERLAY/patch-packages/$PACKAGE_SHA256" \
    --body-file "$PATCH_ARCHIVE" \
    --content-type application/vnd.eden.patch-package.v2+tar --confirm
```

2. **Approve and activate.** Enroll the publisher key, attest host software inventory, and inspect the configuration returned by import. Obtain independent host approval. Sign the typed statement with the matching SDK. Send the admit action followed by activate for the prepared operation. Use the applicable typed payload for each action in `authority-action.json`.

```sh
eden api request POST "/api/v1/interlays/$INTERLAY/native-authority" \
  --body-file authority-action.json --content-type application/json --confirm
```

3. **Verify the operation.** Read the receipt through the same endpoint. Confirm `serving_now` and the full expected shard acknowledgment (32/32 shards in every recorded run). Repeat the benign and marked probes and check the backend observations.
4. **Revoke or restore.** Send revoke with the exact operation UUID. Mandatory protection can refuse traffic until a compatible operation is approved and activated. In every recorded run, revocation failed the interlay closed (503) rather than re-exposing the route.

**Vendor update.** Oracle released a patch at 13:00 PT on November 17, 2026. All Java users should update immediately. On x86-64 hosts, starting OpenJDK with `-XX:-UseBASE64Intrinsics` or `-XX:UseAVX=2` removes the vulnerable intrinsic until the fixed release is deployed. (OpenJDK on ARM does not recognize `UseAVX` and will fail to start with it.)

## Affected-product verification on real AVX-512 hardware (2026-11-17/18 UTC)

The module was verified against real software on **two hosts**: Eden runs on the qualification host (Ryzen 9 3950X / Zen 2, no AVX-512), and the vulnerable application runs on a dedicated verification host — **AWS `m7i.large`, Xeon Platinum 8488C (Emerald Rapids)**, which has the advisory's required CPU flags (`avx512f avx512bw avx512vbmi bmi2`, verified with the advisory's own check command). The application is a real JDK HTTP handler that decodes attacker-controlled Base64 from a `POST /api/decode` JSON field and from `Authorization: Basic` credentials with `java.util.Base64`, decodes each value into a fresh 4096-byte array (the vendor PoC's bounded shape), records a decode audit of every value that reaches the decoder, and starts a 200,000-decode warm-up exactly as the vendor's WARM phase documents. The interlay upstream points at the application through a TCP forwarder, so every probe transits the full Eden lifecycle: real request → module evaluation → real decoder.

The oracle has two parts, both recorded per run: the response body (the application reports each decode attempt's `changed`/`first`/`last` byte scan, which carries the corruption signature on affected hardware) and the application's audit log (whether a value reached the real decoder at all).

| Stage | Observation (single run, Temurin 21.0.13) |
| --- | --- |
| Baseline (unprotected interlay) | Every probe returned 200 and reached the real decoder. Benign values decoded normally. The trigger values raised the decoder's real `IllegalArgumentException` and **corrupted the heap**: the response carried `changed=62 first=50 last=111` (65-byte trigger), `changed=62` (66-byte `==` variant), and `changed=110 first=50 last=159` (129-byte trigger) — the vendor's documented signatures, reproduced through the real HTTP surface. |
| Module active (`gabriel_j4s_v1`, 32/32 shards) | The same trigger requests returned **403 at the Eden boundary** and the audit recorded **no new attack entry** — the malformed values never reached the real decoder, so no corruption was possible. Every benign probe passed with HTTP 200 and decoded with the same byte counts as the baseline (including the near-miss values: 64 characters without padding, and 63 characters + `=`). `GET /health` outside the guarded route passed unchanged. |
| After revocation | The interlay **failed closed** (503 for both the trigger and a benign probe) rather than silently re-exposing the decode route. |

All twenty runs were uniform where it matters: in the baseline every trigger transited to the real decoder (the audit proves it) and corrupted the heap on every affected runtime; with the module active every trigger request was refused 403 at the boundary and **no attack value reached the application** (no corruption was possible); every benign probe passed and decoded; and revocation failed the interlay closed (503). "403 ×4" counts the four trigger values (65-byte and 129-byte body fields, the 66-byte `==` variant, and the Basic-credentials form); "200 ×6" the six benign probes.

**Which versions corrupt by default (recorded).** On the AVX-512 verification host, every 17-line build corrupted **with default flags** (`UseBASE64Intrinsics` defaults on when the CPU advertises EVEX; on the Zen 2 qualification host the same builds default the flag off — the default is CPU-conditional). Every 21+ runtime corrupted by default (`UseAVX=2`, `UseBASE64Intrinsics=true`). The 65-byte trigger corrupts on 21+; the 129-byte trigger corrupts on both 17 and 21+ (the advisory's threshold description held exactly). **JDK 11 did not corrupt** (`changed=0`; the 129 shape's 46 changed bytes were normal in-bounds decode output), matching the advisory's 17.0.6 floor.

**Standalone PoC sweep (22 images, recorded).** The vendor's sweep trigger (both lengths, fresh container per image) ran on every image above plus JDK 8: all 17s reproduced with 129 by default; all 21+ reproduced with 65; **Temurin 8 and Corretto 8 (`1.8.0_512`) did not reproduce** on either length. Oracle's advisory lists `8u511b33-perf` as vulnerable, but that Oracle-specific build has no public container image and could not be tested; the public OpenJDK 8 builds do not reproduce.

**PoC-vs-application discrepancies (honest findings).** Three runtimes showed the single-threaded standalone PoC **failing to reproduce what the real application reproduced**: **GraalVM Community 21** printed `NOT REPRODUCED` standalone but corrupted (`changed=62`) through the application's multi-threaded profile (background warm-up thread + 8-thread HTTP executor) — the application JIT profile compiles the vulnerable intrinsic where the PoC's single-threaded profile did not. **Zulu 25** and **SapMachine 21** printed `NOT REPRODUCED` for the 129-byte shape standalone but corrupted through the application. The lesson recorded for practice: a standalone trigger is a *sufficient* signal when it reproduces, but a clean standalone result can *understate* what a real application does — and Eden's module refuses the shapes regardless of which JIT profile compiles them.

**Coverage notes (honest).** Oracle's advisory lists `17.0.21.0.3`, `21.0.13.0.3`, `25.0.5.0.3`, `27.0.1.0.3` as vulnerable — all four are directly covered (Zulu/Liberica/SapMachine 17.0.21.0.3 and 21.0.13.0.3, Zulu 25.0.5.0.3, Oracle Container Registry 27.0.1.0.3). `8u511b33-perf` could not be tested (no public image). The `openjdk` Docker Official Image line no longer publishes current JDKs, so OpenJDK 25 coverage came from Temurin, Corretto, Zulu, and Oracle's own registry image. `ghcr.io/graalvm/jdk:21` resolves to GraalVM Community 21.3 on JDK 17.0.4 — below the 17.0.6 floor — and was recorded as out-of-range; GraalVM coverage uses `ghcr.io/graalvm/jdk-community:21` (JDK 21.0.2).

**Hardware gate (recorded, not assumed).** The qualification host (Zen 2) cannot compile the vulnerable intrinsic; forcing the flag there produces the JVM's own warning (`Base64 intrinsic requires EVEX instructions on this CPU`), and the same vendor trigger prints `NOT REPRODUCED` with `changed=0`. Every corruption signature quoted above comes from the AVX-512 verification host.

**Gateway finding (defense in depth).** Eden's interlay waits for the complete request body before releasing it upstream. The advisory's own limitations section states that the current remote heap-grooming profiles need partial request bodies to reach the application and that a proxy that waits for the complete body removes their release timing. Eden does exactly that, so the published grooming profiles cannot run through the interlay. The advisory also states request buffering is *not* a general mitigation (single-complete-request chains such as Elasticsearch still work, and WebSocket tunnel frames bypass it), so this property is recorded as defense in depth alongside the module — not as a substitute for the vendor patch.
