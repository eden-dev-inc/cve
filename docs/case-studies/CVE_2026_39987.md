# marimo: unauthenticated terminal command execution (CVE-2026-39987)

The marimo notebook server's terminal WebSocket skips the login check, so a remote unauthenticated caller gets an interactive shell on the host — as root in the default Docker deployment. The advisory reports active exploitation, so an exposed instance should be treated as compromised.

## The vulnerability

marimo's terminal endpoint executes shell input from the WebSocket stream without authenticating the session, giving an unauthenticated remote caller a shell with the server's privileges. Eden fronts the notebook server, so the terminal route rides an HTTP request Eden can refuse before release; on the tested interlay the upgrade handshake is refused at the gateway, and the recorded comparison uses the command-delivery shape.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on `/terminal` and its descendants. This is a coarse rule: it also blocked the benign authenticated terminal request, which is the recorded false positive.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/terminal",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** `gabriel_marimo_v1` waits for a complete request, matches targets starting with `/terminal`, and refuses non-GET requests that carry no `X-Marimo-Session` header. Requests presenting the session header continue, which passed the benign authenticated probe.

```rust
const ROUTE: &[u8] = b"/terminal";
// refuse non-GET without x-marimo-session
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-39987/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded marimo version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source.
2. **Apply the declarative policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged. Full command sequences are in the [API example](../../cve/CVE-2026-39987/http-request-filter/api.md).
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the advisory-shaped request no longer succeeds; re-approve, re-admit, and reactivate a replacement operation to restore protection. Keep the route isolated during the change window.

**Vendor update.** Apply the fix for the installed release line. The [advisory](https://github.com/marimo-team/marimo/security/advisories/GHSA-2679-6mx9-h9xc) documents affected versions and update guidance.

## Fixture and probes

The benign probe posted a shell command to `/terminal/ws` with a session header, as an authenticated client would. The advisory-shaped probe posted `os.system('id')` without a session. The fixture incremented its marker when an unauthenticated command reached the terminal handler. The 1.103.0 HTTP/1 interlay answers 501 to `Upgrade`-bearing requests, so the WebSocket handshake itself could not transit this delivery profile and the fixture carried the command as a POST body.

## Measured comparison (2026-11-13 UTC)

The values after each status are the observed increases in the fixture's terminal-execution counter. The declarative tier blocked the benign probe (the recorded false positive); the module refused only the sessionless command.

| Probe | Baseline | Declarative policy | Native module |
| --- | --- | --- | --- |
| Benign sessioned terminal POST | 200, 0 | 403, 0 | 200, 0 |
| Advisory-shaped sessionless command | 200, 1 | 403, 0 | 403, 0 |

The lab delivered the terminal command as a POST because the interlay does not complete WebSocket upgrades. The module requires a session header on non-GET terminal requests; it does not validate the session value, so a stolen-but-invalid session header would pass the module and is a bypass to record. The 501-on-upgrade behavior is a product finding, not a protection claim.

Product finding recorded during the run: the 1.103.0 HTTP/1 native interlay returns `501 HTTP upgrade and expectation are unsupported` for `Upgrade`-bearing requests, so WebSocket delivery shapes cannot be compared through this profile.

## Test scope

The fixture used an HTTP POST because the interlay did not support WebSocket upgrades. The actual terminal WebSocket exploit path remains unverified. The module checks for a session header without validating its value.
