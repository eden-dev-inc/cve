# Paymenter Livewire Confirmed Action (CVE-2026-103026)

An authenticated (or, for the Paymenter case, unauthenticated) remote caller can submit the vendor-documented crafted parameter to a paymenter 1.4.3 deployment and reach command execution or arbitrary file read. Update to the vendor's fixed release.

**Result.** The vendor-documented attack shape reached the fixture's simulated sink on every attack probe in the baseline, and the native module refused each one with HTTP 403 before release — no crafted parameter reached the sink while the module served — while every benign probe kept HTTP 200, including the same-route other-action controls that must keep passing. After revocation the interlay failed closed rather than silently re-exposing the route, and a replacement operation restored the refusal.

## The vulnerability

Paymenter through 1.4.3 (fixed in 1.4.4) exposed a public Livewire action
`executeConfirmedAction` on every client-facing component
(`app/Livewire/Traits/HasConfirmation.php`): it dispatches to any public method
that exists on the component (`method_exists` — no allowlist), so an
unauthenticated caller re-enters the whole inherited framework API, most
importantly `InteractsWithProperties::fill()` — which writes any public property
including `#[Locked]` ones, with dotted paths reaching into hydrated Eloquent
models (attacker-controlled server-side state). Livewire dispatches any public
method named in an update payload, so the primitive rides the standard Livewire
update POST. Fixed in 1.4.4 (the trait method was dead code, now removed).

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies `POST` on the `/livewire/update` route family. This is a coarse rule: it also blocks the benign probes on the same route (recorded false positives).

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [
            "POST"
          ],
          "path": "/livewire/update",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** Refuse livewire update payloads naming `executeconfirmedaction` (the unauthenticated method re-entry primitive). Detection is scoped to the vendor-documented vulnerable controller/action pair (the `controller=`/`action=` gates), so other actions on the same route keep passing — verified by the same-route control probes.

```rust
const NEEDLE: &[u8] = b"executeConfirmedAction";

fn lower(b: u8) -> u8 {
    if b.is_ascii_uppercase() { b + 32 } else { b }
}

fn is_hex(b: u8) -> bool {
    (b >= b'0' && b <= b'9') || (b >= b'a' && b <= b'f') || (b >= b'A' && b <= b'F')
}

fn hex_val(b: u8) -> u8 {
    match b {
        b'0'..=b'9' => b - b'0',
        b'a'..=b'f' => b - b'a' + 10,
        _ => b - b'A' + 10,
    }
}

fn find_ci(hay: &[u8], needle: &[u8]) -> bool {
    if hay.len() < needle.len() { return false; }
    'o: for i in 0..=(hay.len() - needle.len()) {
        for (j, nb) in needle.iter().enumerate() {
            if lower(hay[i + j]) != lower(*nb) { continue 'o; }
        }
        return true;
    }
    false
}

fn is_livewire_update(head: &[u8]) -> bool {
    // Livewire update posts carry the vendor content type or hit the
    // conventional update route.
    if find_ci(head, b"/livewire/update") {
        return true;
    }
    find_ci(head, b"content-type: application/vnd.livewire")
}
```

**Stated limits.** the scan matches the method-name token on the raw update payload, so a deployment
whose component payloads legitimately carry that literal string in a data value
(not a method name) must narrow the conditions. Durable fix: Paymenter 1.4.4.

## Fixture and probes

The fixture mirrors the vendor-documented request shapes (source references cited above); its oracle records a `103026-injected` effect when the crafted parameter reaches the sink on the vulnerable action.

## Signed module authority

Import returned HTTP 201 with explicit activation required and signature verification deferred. Read-only inspection was refused (403) for the reader principal, admission of a tampered statement was rejected (400), and admission of an invalid signature was refused (403). The activation receipt reported the module serving on all 32 expected shards. After revocation the marked probe received HTTP 503 (fail-closed); re-approval and reactivation restored the refusal.
