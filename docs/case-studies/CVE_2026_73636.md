# Apache mod_auth_digest: one-time-nonce replay attack (CVE-2026-73636)

An attacker able to capture Digest credentials in transit can replay them through the affected Apache shared-state handling. Upgrade mod_auth_digest to protect accounts against reuse of captured authentication material.

Eden terminates the HTTP connection to the affected product, evaluates a

**Status: Declarative route-deny fixture comparison recorded.** The fixture ran against Eden 1.103.0.

## The vulnerability

mod_auth_digest one-time nonces can be replayed within their validity window (high, 8.1). The replay itself is stateful — a stateless request-stage module cannot detect nonce reuse, so no tier-2 module exists; the tier-1 window deny is the honest boundary control.

## The Eden patch

**Tier 1 — declarative policy (blunt, fail-closed):** deny every request under
`/digest` (non-slash scope), legitimate traffic included — false positives
measured below.

**Tier 2:** the case records a declarative result. The test scope below explains the native module limitation.

## Implement the remediation

Use this procedure in an isolated fixture to reproduce the scoped restriction. Follow the vendor update for the underlying exposure. See [deployment prerequisites](../deployment.md).

1. **Prepare the target.** Verify the loaded product and version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use this reconstruction of the report’s scoped fixture deny.
2. **Apply the declarative policy.** Scope the policy to `/digest` and descendants (all methods, `deny`). Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Run an authenticated `GET /api/v1/interlays/{interlay}` with `X-Eden-Verbose: true`. Save its complete current settings object as `current-settings.json` and retain the prior remediation declaration for recovery. Set `IDEMPOTENCY_KEY` to a fresh key for this intended mutation.

Save the declaration as `remediation.json`.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/digest",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```



```sh
jq -e --slurpfile policy remediation.json \
  '.remediation = $policy[0] | {settings: .}' current-settings.json \
  > interlay-update.json
eden api request PATCH "/api/v1/interlays/$INTERLAY" \
  --header "Idempotency-Key:$IDEMPOTENCY_KEY" \
  --body-file interlay-update.json --content-type application/json --confirm
```

3. **Verify the serving policy.** Read back the interlay.

```sh
eden api request GET "/api/v1/interlays/$INTERLAY" \
  --header 'X-Eden-Verbose:true'
```

Check that `remediation_status.state` is `ready` and both desired and effective SHA-256 values match the intended declaration. Replay the benign and marked requests in the recorded comparison on an isolated target. Check the recorded response and backend outcome for each probe.
4. **Restore the previous policy.** Coordinate the change with any other operator updating this interlay. Read current settings again and merge the saved remediation field into them. If the prior settings had no remediation field, omit it in the replacement. Send the same PATCH with a fresh idempotency key, then read back the intended state. Repeat the verification probes. Keep the affected route isolated if restoring the prior settings reopens exposure.

**Vendor update.** Use the [advisory](https://httpd.apache.org/security/vulnerabilities_24.html) to identify the supported update or workaround for the installed release. The advisory data used here supplies no fixed version. Confirm the running version and verify the affected feature after the change.
