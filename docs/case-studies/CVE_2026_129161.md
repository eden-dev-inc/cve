# free-fs: account takeover via brute-forced reset codes (CVE-2026-129161)

An unauthenticated attacker can request a six-digit password-reset code for a known email address and submit unlimited guesses against `PUT /apis/user/forget-password` during the code's 300-second lifetime. A guessed code sets a chosen password and takes over the account. No fixed release is listed at disclosure time, so any reachable instance remains guessable.

## The vulnerability

The reset endpoint accepts the six-digit code with no attempt limiting, so the code can be repeatedly guessed during its 300-second lifetime. Eden fronts the free-fs API, so every guess rides an HTTP request Eden can refuse; the fixture requires a header that an application would need to validate against the session that requested the code.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies PUT on `/apis/user/forget-password` and its descendants. This blocks every reset confirmation, benign or not (the recorded false positive) — an emergency posture that trades the reset feature for account safety.

```json
{ "version": 1, "profile": "http-structure-v1", "policy": { "version": 1, "rules": [ { "scope": { "methods": ["PUT"], "path": "/apis/user/forget-password", "descendants": true }, "require": { "kind": "deny" } } ] } }
```

**Tier 2 — native Rust module.** `gabriel_freefs_v1` waits for a complete request, matches PUTs to `/apis/user/forget-password`, and refuses a code-bearing confirmation that carries no `X-Reset-Session` header — the request-session binding a hardened reset flow would demand. Confirmations presenting the binding header continue.

```rust
const ROUTE: &[u8] = b"/apis/user/forget-password";
// refuse PUT code-confirmations without x-reset-session
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-129161/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded Dromara free-fs version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source.
2. **Apply the declarative policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged. Full command sequences are in the [API example](../../cve/CVE-2026-129161/http-request-filter/api.md).
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the marked fixture request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** Check the advisory and the vendor's release channel for a fix. Restrict the affected feature's exposure while a fix is unavailable. [Advisory reference](https://vul.yulun.ac.cn/20261024/free-fs/)

## Fixture and probes

The benign probe confirmed a reset carrying the `X-Reset-Session` header, as a bound confirmation would. The marked fixture probe submitted a guessed code with no binding. The fixture incremented its marker when an unbound confirmation changed the account password.

## Measured comparison (2026-11-13 UTC)

The values after each status are the observed increases in the fixture's effect counter.

| Probe | Baseline | Declarative policy | Native module |
| --- | --- | --- | --- |
| Benign bound confirmation | 200, 0 | 403, 0 | 200, 0 |
| Advisory-shaped unbound guess | 200, 1 | 403, 0 | 403, 0 |

The module is stateless: it cannot count attempts, so it requires the header without authenticating the binding. A deployment that keeps the stock endpoint but cannot add the binding header should use the tier-1 deny and lose the reset feature, or add app-side attempt limits. Code entropy and expiry remain application properties.

## Test scope

The module checks whether the reset header is present. It cannot verify its binding to a request or count guesses. A deployment needs trusted session validation and attempt limits at the application.
