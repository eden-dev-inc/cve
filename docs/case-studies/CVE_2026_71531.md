# PrestaShop: cross-shop access via Webservice API scope override (CVE-2026-71531)

A PrestaShop Webservice API key restricted to a single shop can read, change, or delete data for every shop the key was never authorized for, by adding parameters such as id_shop=all — remotely, over the network, with nothing but the restricted key. Multistore deployments leak across tenant boundaries wholesale.

## The vulnerability

The Webservice API scopes keys to one shop but applies caller-supplied scope parameters without checking them, so a restricted key reaches every tenant. Eden fronts the shop's API, so the scope-override request rides an HTTP request Eden can refuse before release.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the recorded fixture route and its descendants. This is a coarse rule: it also blocked the benign probe on the same route, which is the recorded false positive.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/api",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** gabriel_psshop_v1 waits for a complete request, matches the API route, and refuses requests whose id_shop parameter names a shop other than the key's own (the module pins the lab key's shop as shop 1) — the scope-override shape the flaw accepts. Requests scoped to the key's own shop continue.

```rust
const ROUTE: &[u8] = b"/api";
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-71531/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded PrestaShop Webservice API version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source.
2. **Apply the declaratory policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged. Full command sequences are in the [API example](../../cve/CVE-2026-71531/http-request-filter/api.md).
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the advisory-shaped request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** The fixed release carries the durable repair; the [advisory](https://cve.now/CVE-2026-71531) links the vendor's update instructions where available. Eden's tiers are an enforcement stopgap for a deployment that cannot upgrade immediately.

## Fixture and probes

The benign probe listed products scoped to the key's own shop (id_shop=1). The advisory-shaped probe sent the same call with id_shop=all. The fixture incremented its marker when a cross-shop scope override reached the API.

## Measured comparison (2026-11-13 UTC)

The values after each status are the observed increases in the fixture's effect counter.

| Probe | Baseline | Declarative policy | Native module |
| --- | --- | --- | --- |
| Benign own-shop API call | 200, 0 | 403, 0 | 200, 0 |
| Advisory-shaped cross-shop override | 200, 1 | 403, 0 | 403, 0 |

The module pins the lab key's authorized shop (shop 1) — an operator must rebuild with their key's own shop, or the SDK must gain configurable scope bindings (a recorded product limitation). Scope overrides reaching legitimately-shared second shops are a bypass to record. The durable fix is the vendor's scope-check patch.
