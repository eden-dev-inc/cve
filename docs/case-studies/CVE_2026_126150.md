# FortiMail: IBE webmail account takeover via weak password recovery (CVE-2026-126150)

An unauthenticated remote caller can reset any IBE webmail user's password and take over the account through FortiMail's password-recovery flow. The attacker needs no login — crafted HTTP requests to the recovery surface are enough.

## The vulnerability

The recovery flow accepts a password reset for a known address without binding the confirmation to the request that initiated it, so an unauthenticated caller completes takeovers. Eden fronts the webmail surface, so the reset rides an HTTP request Eden can refuse before release.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the recorded fixture route and its descendants. This is a coarse rule: it also blocked the benign probe on the same route, which is the recorded false positive.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/fortimail_ibe/reset",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** gabriel_fmreset_v1 waits for a complete request, matches the IBE reset route, and refuses a reset confirmation carrying an email address without a recovery binding header (X-FM-Recovery) — the binding a hardened recovery flow would demand.

```rust
const ROUTE: &[u8] = b"/fortimail_ibe/reset";
// refuse reset confirmations without x-fm-recovery binding
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-126150/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded Fortinet FortiMail version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source.
2. **Apply the declaratory policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged. Full command sequences are in the [API example](../../cve/CVE-2026-126150/http-request-filter/api.md).
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the advisory-shaped request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** Apply the vendor update for the installed release or model. [Advisory reference](https://fortiguard.fortinet.com/psirt/FG-IR-26-202)

## Fixture and probes

The benign probe confirmed a reset presenting the recovery binding header. The marked fixture probe submitted the reset without the binding. The fixture incremented its marker when an unbound reset reached the recovery handler.
