# Airflow: unquoted dag_run.conf template pattern to command injection (CVE-2026-42252)

Apache Airflow's official documentation ('Passing Parameters when triggering Dags') showed a verbatim BashOperator(bash_command="echo value: {{ dag_run.conf['conf1'] }}") example without quoting or sanitization warnings. Dag authors who copied the pattern verbatim into deployments where users held can_trigger permission let those users inject shell commands through conf values.

## The vulnerability

The documented pattern interpolates dag_run.conf values into shell commands unquoted, so a user with trigger permission injects OS commands through the conf field. Eden fronts the webserver, so the conf-bearing trigger rides an HTTP request Eden can refuse before release.

## The Eden patch

**Tier 1 — declaratory policy.** The recorded policy denies every method on the recorded route family and its descendants. This is a coarse rule: it also blocked the benign probe on the same route, which is the recorded false positive.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/api/v1/dags",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** airflow_dagrun_conf_template_guard waits for a complete request, matches POSTs on the dagRuns trigger route, and refuses bodies carrying shell metacharacter or SQL markers (;, $(, backtick, ' OR, union select) — the injection family the example-DAG and parameter flaws expose. Clean trigger bodies continue.

```rust
static MARKS: [&[u8]; 5] = [b";", b"$(", b"`", b"' or", b"union select"];
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-42252/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded Apache Airflow (documentation pattern) version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission.
2. **Apply the declaratory policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged.
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the advisory-shaped request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** The fixed release carries the durable repair; the [advisory](https://cve.now/CVE-2026-42252) links the vendor's update instructions where available. Eden's tiers are an enforcement stopgap for a deployment that cannot upgrade immediately.

## Fixture and probes

The benign probe triggered with a clean conf value (value1). The advisory-shaped probe supplied a conf value carrying a metacharacter command — the documentation pattern's injection shape. The fixture incremented its marker when an injected conf value reached the command construction.

## Affected-product verification (Apache Airflow 2.10.5, 2026-11-14 UTC)

After the fixture comparison, the same chain was verified against the real product: Apache Airflow 2.10.5 (official image) with CeleryExecutor, Redis broker and a PostgreSQL metadata database, fronted by an Eden interlay. The vulnerable operation is the documentation pattern itself, instantiated in a real DAG file (`BashOperator(bash_command="echo value: {{ dag_run.conf['conf1'] }}")`).

| Stage | Observation |
| --- | --- |
| Baseline (unprotected interlay) | `POST /api/v1/dags/vuln_pattern_dag/dagRuns` with `conf.conf1 = value;id` returned 200; the real worker log recorded `Running command: ['bash','-c','echo value: value;id']` and the injected command's output — `uid=50000(root)`. The pattern executes as root in the default container. |
| Module active | The same trigger was refused at the Eden boundary (403). The real worker log was unchanged after the wait window (no new task instance, no rendered command), and a subsequent benign trigger still passed (200) and executed normally in the real worker. |
| Oracle | The real worker's task logs under `/opt/airflow/logs`, read directly from the worker container — independent of both gateway responses. |

The exact CVE (a documentation advisory) is not a code flaw in 2.10.5; the verification shows the documented pattern is a working unquoted-injection chain in a real deployment whose DAG authors follow it, which is the advisory's stated risk.

Product finding recorded during this verification: with a native module active, an interlay whose endpoint target is a **DNS hostname** fails every request with `501 [E1A54] Original HTTP forwarding profile is unsupported`; the same module on the same upstream works when the target is an **IP address**. All fixture-based waves used IP targets, so this was not observable in the synthetic runs. Operators should pin interlay endpoint targets to IP addresses (or qualified addresses validated by their Eden version) until E1A54 is fixed.
