# eXtplorer: login bypass and PHP upload to remote code execution (CVE-2023-54335)

eXtplorer 2.1.14 lets an attacker bypass the file manager login and upload PHP files. When the server executes those files, the attacker can run commands with the web process's privileges.

## The vulnerability

The affected versions and upgrade guidance are listed above. The Eden policy and module were tested against the HTTP fixture described below.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the recorded fixture route and its descendants. This is a coarse rule: it also blocked the benign probe on the same route, which is the recorded false positive.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/extplorer",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** gabriel_extplorer_v1 waits for a complete request, matches the eXtplorer upload action, and refuses bodies naming PHP upload targets (.php, phar:, phtml).

```rust
static MARKS: [&[u8]; 3] = [b".php", b"phar:", b"phtml"];
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2023-54335/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded eXtplorer version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source.
2. **Apply the declaratory policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged. Full command sequences are in the [API example](../../cve/CVE-2023-54335/http-request-filter/api.md).
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the marked fixture request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** Follow the update instructions for the installed product and release line. [Vendor or publisher advisory](https://www.vulncheck.com/advisories/extplorer-authentication-bypass-remote-code-execution-rce)

## Fixture and probes

The benign probe uploaded a PDF. The marked fixture probe uploaded a .php file. The fixture incremented its marker when a PHP upload reached the file handler.

## Signed module authority

Import returned HTTP 201 with explicit activation required and signature verification deferred. Read-only inspection was refused (403) for the reader principal, admission of a tampered statement was rejected (400), and admission of an invalid signature was refused (403). The activation receipt reported the module serving on all 32 expected shards. After revocation the marked fixture probe received HTTP 503 (fail-closed); re-approval and reactivation restored the refusal (403, counter unchanged).
