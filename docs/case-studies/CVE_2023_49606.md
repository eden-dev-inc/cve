# Tinyproxy: use-after-free in Connection header parsing (CVE-2023-49606)

An unauthenticated caller can corrupt Tinyproxy's memory through crafted Connection headers: a specially shaped value frees memory that later parsing reuses, and the advisory rates the outcome potential remote code execution. Anyone who can reach the proxy port can trigger it — no login.

## The vulnerability

Tinyproxy's connection-header parser frees and reuses memory on crafted values, reachable unauthenticated by anyone who can reach the proxy port. Eden fronts Tinyproxy, so the crafted Connection value rides an HTTP request Eden sees before release — but on the tested interlay the gateway consumes hop-by-hop headers itself and validates connection options (invalid option shapes returned 400 before any policy).

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the proxied status route and its descendants. This is a coarse rule: it also blocked the benign proxied request, which is the recorded false positive.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/status",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** gabriel_tinyproxy_v1 refuses Connection header values longer than 64 bytes or carrying more than five comma-separated options. The module imported and activated on all 32 shards — and then did not refuse the advisory-shaped Connection value, because the interlay does not present hop-by-hop headers to module evaluation. The module tier is recorded as not demonstrable for this delivery shape.

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2023-49606/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded Tinyproxy version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Use the recorded declaration and the linked source.
2. **Apply the declarative policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Verify the recorded outcome.** The active native module did not see the hop-by-hop Connection header, and the crafted request reached the backend. The documented route-wide declarative deny blocked both probes. Verify any deployment against the affected proxy and apply the vendor fix.

**Vendor update.** Apply the fix for the installed release line and verify the application behavior after upgrading. [Advisory reference](https://github.com/tinyproxy/tinyproxy/releases/tag/1.11.2)

## Fixture and probes

The benign probe sent Connection: keep-alive. The marked fixture probe sent a 49-byte value of seven comma-joined close tokens. The fixture incremented its marker when the crafted value reached its parser.

## Measured comparison (2026-11-13 UTC)

The values after each status are the observed increases in the fixture's effect counter.
