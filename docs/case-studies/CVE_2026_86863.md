# pgAdmin 4: webserver-authentication bypass via client-supplied identity header (CVE-2026-86863)

An unauthenticated attacker who can reach an affected pgAdmin 4 instance with Webserver authentication enabled can impersonate a user, including an administrator. A successful attack can expose server definitions and stored credentials and give the attacker control of the pgAdmin instance, so affected deployments should upgrade.

**Result.** In the synthetic fixture, the marked login request reached the backend and incremented its admin-login counter. The policy and module each returned HTTP 403 with no counter increase. The native module passed the ordinary browse request and the route-wide policy blocked it.

## The vulnerability

The vulnerable authentication handler falls back to an HTTP header named by the Webserver authentication configuration when the corresponding WSGI environment value is absent. A reachable client can supply that header and claim the identity of an existing user.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the fixture browse route and its descendants. It also blocked the ordinary browse probe.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/browser",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** The module waits for a complete request and refuses the X-Remote-User header on targets starting with /browser. Position any authorized identity assertion downstream of the filter and verify the actual route, configured header, and proxy trust settings before considering the rule for a deployment.

```rust
const ROUTE: &[u8] = b"/browser";
// refuse requests presenting X-Remote-User
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-86863/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded pgAdmin 4 version against the advisory and check whether AUTHENTICATION_SOURCES enables webserver. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission.
2. **Apply the declarative policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged.
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the identity-bearing request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** Upgrade to pgAdmin 4 9.18 or later. Review the trusted proxy settings in the release notes if your deployment uses a header assertion. [pgAdmin 4 9.18 release notes](https://www.pgadmin.org/docs/pgadmin4/9.18/release_notes_9_18.html)

## Signed module authority

Import returned HTTP 201 with explicit activation required and signature verification deferred. Read-only inspection was refused (403) for the reader principal, admission of a tampered statement was rejected (400), and admission of an invalid signature was refused (403). After revocation the advisory-shaped probe received HTTP 503 (fail-closed); re-approval and reactivation restored the refusal (403, counter unchanged).

## Test scope

The test used a synthetic authentication handler and the example X-Remote-User header. It did not run pgAdmin or exercise its login endpoint or trusted proxy configuration. The module checks that one header name case-insensitively on paths starting with /browser. It does not verify identity, cover other routes, or match a differently configured identity header.
