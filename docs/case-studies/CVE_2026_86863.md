# pgAdmin 4: webserver-authentication bypass via client-supplied identity header (CVE-2026-86863)

pgAdmin 4's Webserver authentication source is designed to accept an identity asserted by the web server or reverse proxy in front of it, delivered through the WSGI/CGI environment. A flaw makes WebserverAuthentication.get_user() fall back to reading the remote-user name directly from the inbound HTTP request when the environment returns nothing — so an unauthenticated remote client who presents the identity header is logged in as that user, including the administrator.

## The vulnerability

WebserverAuthentication.get_user() reads the remote-user identity from the WSGI/CGI environment, which a trusted fronting proxy populates. When that environment value is empty, it falls back to reading the same name from the inbound HTTP request headers — a source any unauthenticated network client controls. An attacker presents X-Remote-User and is authenticated as that identity. Eden terminates the client connection in front of pgAdmin, so every header the client sends transits an interlay where a policy or module can refuse the spoofed assertion before release.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the browser route and its descendants. This is a coarse rule: it also blocked the ordinary unauthenticated browse, which is the recorded false positive — worse than usual, because for this flaw the benign shape *is* the unauthenticated request.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/browser",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** `gabriel_pgwebauth_v1` waits for a complete request, matches targets starting with the browser route, and refuses any request presenting an X-Remote-User header — the identity-assertion name WebserverAuthentication trusts. Ordinary requests without the assertion header continue. On a deployment where the trusted proxy injects the identity after Eden, the module keeps working: the client-side copy is refused, the proxy-side injection never transits the interlay with that header.

```rust
const ROUTE: &[u8] = b"/browser";
// refuse requests presenting X-Remote-User
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-86863/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded pgAdmin 4 version against the advisory and confirm WEB_SERVER mode is in use. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission.
2. **Apply the declarative policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged.
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the identity-bearing request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** The fixed release carries the durable repair: WebserverAuthentication must not fall back to untrusted request headers for the environment-injected identity. Eden's tiers are an enforcement stopgap for a deployment that cannot upgrade immediately.

## Fixture and probes

The benign probe fetched the pgAdmin browse route unauthenticated. The advisory-shaped probe fetched the same route presenting `X-Remote-User: admin` — the identity-spoofing shape the advisory describes. The fixture incremented its marker only when a client-supplied identity header reached the authentication handler and logged the request in.

## Measured comparison (2026-11-13 UTC)

The values after each status are the observed increases in the fixture's admin-login counter.

| Probe | Baseline | Declarative policy | Native module |
| --- | --- | --- | --- |
| Benign unauthenticated browse | 200, 0 | 403, 0 | 200, 0 |
| Advisory-shaped identity spoof | 200, 1 | 403, 0 | 403, 0 |

The module rule is the inverse shape of the usual IDOR bindings: instead of refusing requests *missing* a session binding, it refuses requests *carrying* a header that only a trusted proxy should inject. This is the same trust-header-spoofing family recorded for CVE-2026-128023 (FrankenPHP dot-header spoof) and CVE-2026-120869 (NetScaler console identity).
