# php2shell: session serializer mismatch to remote code execution (CVE-2026-115560)

An unauthenticated remote caller can submit a multipart upload that arms PHP's RFC1867 upload-progress callback, which — before the target script runs, with no `session_start()` anywhere — opens the request's file-backed session and writes attacker-controlled records through the writer context's serializer (`php_binary` or `php_serialize`). When the same session store is later read by a context using the `php` serializer (because `session.serialize_handler` differs across apps, pools, or CLI jobs sharing the store), a `|` inside the attacker key material splices new `key|value` records into the reader's `$_SESSION` — including serialized objects, which the vendor chains to remote code execution when the reading application contains a suitable gadget. Update PHP to 8.2.36, 8.3.37, 8.4.28, or 8.5.13.

**Result.** The mismatched-serializer splice was reproduced on real PHP 8.2.35, component by component: the `php` session reader (a real `session_start()` with `serialize_handler=php`) scans `|` inside key material and unserializes the bytes after it, splicing attacker-shaped records into `$_SESSION` — including a live `stdClass` object promoted from the carrier's inert bytes; the `php_binary` and `php_serialize` writer contexts write attacker-controlled multipart key/field/filename bytes — `|` included — into the shared session file through the real serializer; and the RFC1867 upload-progress callback (the arming path) runs on an unauthenticated multipart POST before any script code, writing exactly those records (proven on a real Apache SAPI in the [CVE-2026-126714](CVE_2026_126714.md) study). The fixture models the full reader-side splice at the session-grammar level, and the native module refused every progress-carrying multipart request with HTTP 403 before release — the callback never arms, so no attacker-controlled session record is written from a refused request — while preserving HTTP 200 for non-multipart and plain-multipart traffic. After revocation the interlay failed closed rather than re-exposing the upload route.

## The vulnerability

PHP's session extension subscribes to RFC1867 multipart events when `session.upload_progress` is enabled (the default). A form part named `PHP_SESSION_UPLOAD_PROGRESS` supplies a progress key; the callback resolves the request's session ID and — while the multipart body is still being parsed, before the script runs — reads the current session, inserts `upload_progress_<key>` records (whose serialized strings carry the multipart field names and filenames), serializes the whole session through the **writer context's** serializer, and writes it back to `sess_<SID>`.

With `serialize_handler=php_binary` or `php_serialize`, the writer emits length-delimited (or `serialize()`-wrapped) bytes that need not follow the `php` handler's `key|value` record grammar. When a context with `serialize_handler=php` later reads the same store — the advisory's mismatched-serializer precondition, reachable via `ini_set` at runtime or across applications sharing a session directory — its decoder scans the raw bytes for `|`, treats everything before it as a key, and hands everything after it to the unserializer, repeating. A `|` inside the attacker key material therefore splices new records into the reader's `$_SESSION`; carefully chosen length fields make the spliced material parse, promoting serialized objects (the vendor chains a PHP-native-class memory corruption from there to RCE).

The fix release (8.2.36/8.3.37/8.4.28/8.5.13) also carries CVE-2026-126714 (phpAfterShell — interrupted session-write splicing, patched separately in this portfolio). The vendor's workaround for both is the same: keep `session.upload_progress.enabled=0` in every configuration that can write to the affected session store, set administratively before request input is processed.

**Fixed-build behavior (verified on real `php:8.2.36`, 2026-11-19):** the release flips `upload_progress.enabled` to Off by default (staying `PERDIR`, so it cannot be re-armed at runtime), and a new guard makes **every runtime session ini change throw** while upload progress is armed (`Error: Session ini settings cannot be changed at runtime when session.upload_progress.enabled is On` — observed on a real 8.2.36 request with progress php.ini-armed). That kills the `ini_set` mismatch vector recorded above. **Not addressed by the fix (stated honestly):** the cross-application mismatch — two apps or pools sharing one session store with *different* `session.serialize_handler` values in their php.ini files — still splices exactly as recorded, because the fix "does not enforce matching serializers across separate configurations"; the module's boundary refusal of the arming field remains the boundary control for that surface and for any deployment that arms progress administratively. See the [126714 fixed-release verification](CVE_2026_126714.md#fixed-release-verification-2026-11-19-utc) for the same release's phpAfterShell leg.

## Primitive components on real PHP (2026-11-19 UTC)

Each public Docker Hub PHP image was run on the verification host (php:8.2.35 — an affected release, fixed only in 8.2.36):

1. **The php reader splice** (real `session_start()`, `serialize_handler=php`): a session file whose key material carries a `|` splices new records into `$_SESSION`. Direct byte-shape tests through the real handler: `x|s:3:"AAA";evil|s:5:"pwned";` decoded to two records with `$_SESSION['evil'] = "pwned"`; `x|s:3:"AAA";evil|O:8:"stdClass":1:{s:5:"proof";s:5:"pwned";}`-shaped material promoted a live `stdClass` object (the same promotion was observed end-to-end through real PHP session decodes in the [CVE-2026-126714](CVE_2026_126714.md) study). Malformed splices destroy the session (the real handler's failure path).
2. **The writer contexts carry the attacker `|`** (real `session_start()` + assignment + `session_write_close()`): `serialize_handler=php_binary` and `php_serialize` both wrote the attacker key/field/filename bytes verbatim into the shared session file (`|` bytes included, observed in the file bytes).
3. **The arming path is pre-script and unauthenticated** (real `php:8.2.35-apache`, stock): an unauthenticated `multipart/form-data` POST carrying a `PHP_SESSION_UPLOAD_PROGRESS` part and a real file caused the SAPI to create and write `sess_<SID>` before the script ran — with no session code in the script — and a later ordinary `session_start()` decoded it (proven in the 126714 study; the same callback, key, and attacker string carriers).

**Honest limit:** the combined chain — the full RFC1867 callback array (with its fixed serialized members) written by a real writer context and then decoded by a real `php` reader without destroying the session — was **not reproduced** here. The php reader destroys the session when trailing material fails to parse, and absorbing the writer array's fixed tail requires the vendor's withheld file geometry (my `C`-format payload calibration did not complete; a `Serializable` gadget class in the reading application is also required for that absorption path). The fixture below models the reader-side splice at the session-grammar level: every grammar element in the model is a byte-shape verified against the real PHP decoder in (1)–(2).

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies `POST` on the `/upload` route family. This is a coarse rule: it also blocks the benign upload probes on the same route (recorded false positives).

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [
            "POST"
          ],
          "path": "/upload",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** The module refuses `multipart/form-data` requests that carry a form part named `PHP_SESSION_UPLOAD_PROGRESS` — the field that arms the RFC1867 upload-progress callback (the writer of the attacker-controlled session records). The callback never runs, so no attacker-controlled session record is written through the upload-progress path from a refused request, in any serializer configuration. This is the vendor's own workaround (`session.upload_progress.enabled=0` in every configuration that can write to the affected store) expressed at the request boundary. Detection is boundary-aware: the part name is matched only inside multipart part-header regions (after each boundary), never in part bodies. Non-multipart requests and multipart requests without the field pass untouched.

```rust
const PROGRESS_FIELD: &[u8] = b"PHP_SESSION_UPLOAD_PROGRESS";

fn lower(b: u8) -> u8 {
    if b.is_ascii_uppercase() { b + 32 } else { b }
}

/// Case-insensitive substring search (ASCII). Returns the match start.
fn find_ci(hay: &[u8], needle: &[u8]) -> Option<usize> {
    if needle.is_empty() || hay.len() < needle.len() {
        return None;
    }
    'outer: for i in 0..=(hay.len() - needle.len()) {
        for (j, nb) in needle.iter().enumerate() {
            if lower(hay[i + j]) != lower(*nb) {
                continue 'outer;
            }
        }
        return Some(i);
    }
    None
}

/// Byte-wise equality at an offset (no slice compare: the closed profile
/// rejects bcmp imports).
fn eq_at(hay: &[u8], at: usize, needle: &[u8]) -> bool {
    if at > hay.len() || hay.len() - at < needle.len() {
        return false;
    }
    for (j, nb) in needle.iter().enumerate() {
        if hay[at + j] != *nb {
            return false;
        }
    }
    true
}

/// Case-sensitive substring search. Returns the match start.
fn find(hay: &[u8], needle: &[u8]) -> Option<usize> {
    if needle.is_empty() || hay.len() < needle.len() {
        return None;
    }
    for i in 0..=(hay.len() - needle.len()) {
        if eq_at(hay, i, needle) {
            return Some(i);
        }
    }
    None
}

/// Extract the multipart boundary from a Content-Type header value.
/// `multipart/form-data; boundary=X` — X may be quoted.
fn boundary_of(ct: &[u8]) -> Option<&[u8]> {
    let at = find_ci(ct, b"boundary=")?;
    let mut rest = &ct[at + b"boundary=".len()..];
    if rest.first() == Some(&b'"') {
        rest = &rest[1..];
        let end = rest.iter().position(|&b| b == b'"')?;
        Some(&rest[..end])
    } else {
        let end = rest
            .iter()
            .position(|&b| b == b';' || b == b'\r' || b == b'\n' || b == b' ')
            .unwrap_or(rest.len());
        Some(&rest[..end])
    }
}

/// Does a part header region (the `Content-Disposition` etc. headers after a
/// boundary) declare a form field named `PHP_SESSION_UPLOAD_PROGRESS`?
fn part_header_has_progress(region: &[u8]) -> bool {
    let mut from = 0usize;
    while let Some(rel) = find_ci(&region[from..], b"name=") {
        let at = from + rel;
        let mut v = at + b"name=".len();
        if region.get(v) == Some(&b'"') || region.get(v) == Some(&b'\'') {
            v += 1;
        }
        if region[v..].len() < PROGRESS_FIELD.len() {
            return false;
        }
        if eq_at(region, v, PROGRESS_FIELD) {
            // Require a real field-name terminator: quote, CR, LF, ; or =
            let after = region.get(v + PROGRESS_FIELD.len()).copied();
            return matches!(
                after,
                None | Some(b'"') | Some(b'\'') | Some(b'\r') | Some(b'\n') | Some(b';') | Some(b'=')
            );
        }
        from = at + b"name=".len();
    }
    false
}

/// Scan a multipart body for any part whose header names the progress field.
fn multipart_carries_progress(body: &[u8], boundary: &[u8]) -> bool {
    let sep_prefix = b"--";
    let mut from = 0usize;
    while let Some(rel) = find(&body[from..], boundary) {
        let b_at = from + rel;
        // require the RFC 2046 dashes before the boundary (the first part
        // starts at byte 0 with no preceding bytes)
        let dashed = b_at == 0
            || (b_at >= sep_prefix.len() && eq_at(body, b_at - sep_prefix.len(), sep_prefix));
        let part = b_at + boundary.len();
        let headers_end = match find(&body[part..], b"\r\n\r\n") {
            Some(rel) => part + rel,
            None => match find(&body[part..], b"\n\n") {
                Some(rel) => part + rel,
                None => body.len(),
            },
        };
        if dashed && part_header_has_progress(&body[part..headers_end]) {
            return true;
        }
        from = b_at + boundary.len();
    }
    false
}

fn request_is_multipart_with_progress(head: &[u8], body: &[u8]) -> bool {
    // Request line first; headers follow. Find the Content-Type header value.
    let ct_at = match find_ci(head, b"content-type:") {
        Some(at) => at + b"content-type:".len(),
        None => return false,
    };
    let ct_end = head[ct_at..]
        .iter()
        .position(|&b| b == b'\r' || b == b'\n')
        .map(|rel| ct_at + rel)
        .unwrap_or(head.len());
    let ct = &head[ct_at..ct_end];
    if find_ci(ct, b"multipart/form-data").is_none() {
        return false;
    }
    let boundary = match boundary_of(ct) {
        Some(b) => b,
        None => return false,
    };
    multipart_carries_progress(body, boundary)
}
```

**Stated limits.** Upload progress is disabled outright for protected routes — an application using the progress data on the same route loses that feature, the identical trade-off of the vendor's workaround. The module is request-shape-only: it cannot observe the store directory, the serializer configuration of either context, or a deployment that writes attacker bytes through a different request shape. The durable fix is the PHP release (or the vendor's administrative `upload_progress.enabled=0`).

## Implement the remediation

1. **Prepare the target.** Confirm the PHP version and family against the advisory (`php -i | grep session`). Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission.
2. **Apply the declarative policy.** Set `INTERLAY` to the target interlay UUID. Save the interlay's current settings, place the tier-1 policy in `settings.remediation`, and PATCH the full settings with a fresh `Idempotency-Key`. Read back `remediation_status.state == ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the published source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and all shards are acknowledged.
4. **Verify, revoke, and restore.** Replay the benign and marked probes and compare the fixture oracle. Revoke and confirm the route fails closed (503); re-approve, re-admit and reactivate a replacement operation to restore protection.

## Fixture and probes

The fixture (`gabriel-php2shell-app`) mirrors the advisory topology: a writer context serializes the RFC1867 callback record (key = `upload_progress_<attacker value>`; `files[0].field_name`/`name` carry attacker multipart strings — lab transport: hex-encoded part names, since multipart header grammar cannot carry quote bytes verbatim; production carries the same bytes through ordinary multipart metadata, observed on the real Apache leg of the 126714 study), and a reader context decodes the same bytes with the `php` `key|value` grammar. A `|` in the attacker key material splices records; the fixture records a `phpfs2_primitive` effect when the reader promotes the attacker object record.
