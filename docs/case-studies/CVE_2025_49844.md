# Redis Lua-script sandbox escape (CVE-2025-49844) through Eden's API

An authenticated Redis user can trigger a Lua garbage-collection use-after-free that may lead to code execution in the Redis process. Update Redis to protect the server and the data accessible to that process.

Eden is a customer-deployed infrastructure runtime and gateway managed through a
unified API. Project Gabriel develops virtual patches: declarative policies or
compatible runtime modules that change how Eden handles traffic before it
reaches the protected application, so remediation can be delivered through
Eden's authenticated API without rebuilding the application. This case
examines closing a Lua-script sandbox escape on a Redis instance without
replacing `redis-server` — and, on inspection, **rejects its own first
candidate patch as a low-quality remediation**.

**Status: not remediated on this product revision.** The Redis remediation
adapter does not exist in the deployed build (verified against the source
tree), and the blanket command-block sketch proposed earlier in this case is
rejected below as a functional restriction, not a remediation. The candidate
stays blocked on two named prerequisites until either they are delivered or
the candidate is replaced per the portfolio rules. **Assessment:** 11 November
2026 UTC. Tracking issue: EDEN-3162.

## The vulnerability

In affected Redis releases, a permitted Lua-script escape allows executing
OS commands from script execution contexts that were meant to be sandboxed,
with the practical exposure depending on enabled modules and configuration
([primary advisory](https://github.com/redis/redis/security/advisories/GHSA-4789-qfc9-5f9q)).
The durable fix is a patched Redis release. The exploitable primitive is a
script-execution context reaching beyond its sandbox — not script execution
itself: sandboxed Lua scripting is the legitimate capability (atomic
multi-key transactions, rate limiters, idempotent check-and-set), and Redis
fleets depend on it.

## The challenge of patching the fleet

Redis sits on the data path of nearly every service in a fleet; upgrading
means coordinated failovers, replica re-provisioning and client-library
compatibility across primary/replica pairs with strict durability
expectations. The vendor's scripting restriction is the interim posture.
A gateway boundary can deliver that restriction — but only if it can see
Redis commands at all, and only if it refuses the right ones.

## What a high-quality Eden patch requires — and what this case rejects

The quality bar for this portfolio, per the maintainer: **remove the exploit
prerequisite while preserving the legitimate capability.** A remediation that
deletes the capability wholesale is the fleet-shutdown pattern in miniature —
valid, costly, blind.

- **Rejected as the case's patch: blanket script-command blocking.** This
  case's earlier sketch proposed refusing `EVAL`/`EVALSHA`/`SCRIPT` under a
  hypothetical `redis-command-v1` policy. That removes the entire scripting
  capability — every atomic transaction, rate limiter and idempotent
  operation built on Lua — to close one sandbox defect. It is defensible
  only as an explicitly labeled emergency brake while a real fix ships, and
  it is **not** recorded here as a delivered remediation.
- **High quality, advisory-grounded: close the specific escape path.** The
  advisory ties practical exposure to enabled modules and configuration —
  the classic Redis sandbox-escape shape is a script context reaching a
  module-loading or configuration path. A surgical command policy refusing
  the escape-path command family (while `EVAL` keeps serving ordinary
  scripts) would preserve scripting; a native `RemediationModule` validating
  script content against the sandbox contract would go further. Either
  requires the actual escape path from the advisory or a PoC — grounding
  this portfolio does not invent.
- **Blocked on two prerequisites, both verified this run:**
  1. **The Redis remediation adapter does not exist in the deployed
     product build.** `eden_gateway/redis` ships watch/flow/comparison and
     migration processing only — verified against the source tree of the
     deployed `d9fe8ee4b6f8` revision. No Redis policy of any shape —
     blanket or surgical — can be activated through Eden's API today.
  2. **No public PoC or escape-path detail is recorded for this CVE** at
     assessment time, so a surgical command selection cannot be grounded
     without inventing vulnerability details, which this portfolio does
     not do.

## Implement the remediation

The Redis assessment did not deploy an Eden command policy. Qualify the patched server with ordinary scripting and application traffic.

1. **Identify the affected installation.** Check the installed component and the advisory’s prerequisites.
2. **Apply the vendor fix.** Use the [advisory](https://github.com/redis/redis/security/advisories/GHSA-4789-qfc9-5f9q) to select the fixed release for the installed branch. Reported fixed releases include `8.2.2`. Follow the vendor’s update instructions and confirm the version actually loaded by the service.
3. **Verify the upgrade.** Confirm the running version and repeat normal operations on the upgraded service. Use an isolated environment for security regression probes.
4. **Restore service if the update fails.** Follow the vendor’s recovery instructions and keep the affected operation isolated until the supported fix is active.

## Results and limits

| Observation | Status |
| --- | --- |
| Escape-path policy (surgical) | **Blocked**: adapter absent (source-verified) + escape path ungrounded (no PoC/advisory detail) |
| Blanket script blocking | **Rejected** as low quality — removes the legitimate capability (the fleet-shutdown pattern, smaller) |
| Candidate disposition | Open-blocked per EDEN-3160/EDEN-3171: deliver the Redis command-policy adapter plus advisory grounding, or replace this candidate with another distinct critical CVE having a complete generic-API protection story |

The patched Redis release remains the durable repair, as in every case.
Redis remediation is also a separate gateway endpoint family from HTTP: even
with the adapter delivered, an HTTP-only qualification (like this run's)
would not qualify it — framing, pipelining, authentication/session state
and every admitted connection path would need their own case protocol, per
the tracking issue.
