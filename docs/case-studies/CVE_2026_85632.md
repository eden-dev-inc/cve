# Unauthenticated Payment Status Manipulation in Sipay's WooCommerce module (CVE-2026-85632)

An attacker can manipulate unauthenticated payment-status messages in the affected Sipay WooCommerce module. Remediate the integration so order fulfillment depends on authenticated and integrity-checked payment confirmation.

**Status: Remediated (tier 1 + tier 2), live-proven 2026-11-11T17:09:25Z on the
installed `eden-product-release:1.103.0` lab container.**

## The vulnerability

Sipay's WooCommerce module exposes a payment-status endpoint that an
unauthenticated caller can drive to flip an order to completed. The fixture
(`make_sipay`, port 18319) reproduces the delivery shape: a status-flip body
(`"status": "completed"`) without an `Authorization` header records a
payment-changed mark; the same body with a merchant bearer passes without
effect.

## The Eden patch

**Tier 1 — declarative policy (blunt, fail-closed):** deny every request under
`/wp-json/wc`, merchant-server status updates included — false positives
measured below.

**Tier 2 — native Rust module `gabriel_sipay_v1` (surgical):** refuses
status-flip bodies that arrive **without an Authorization header**;
authenticated merchant-server updates pass unchanged.

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md).

1. **Prepare the target.** Verify the loaded product and version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission. Open the [deployment example](../../cve/CVE-2026-85632/http-request-filter/deployment.json) and [API instructions](../../cve/CVE-2026-85632/http-request-filter/api.md). The bundle identifies registry package `sipay-woocommerce-payment-status-guard` at version `1.0.0` and the SDK revision in [patch.toml](../../cve/CVE-2026-85632/http-request-filter/patch.toml). Run the policy extraction from the adapter directory.
2. **Apply the declarative policy.** Scope the policy to `/wp-json/wc` and descendants (all methods, `deny`). Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Run an authenticated `GET /api/v1/interlays/{interlay}` with `X-Eden-Verbose: true`. Save its complete current settings object as `current-settings.json` and retain the prior remediation declaration for recovery. Set `IDEMPOTENCY_KEY` to a fresh key for this intended mutation.

```sh
jq -e '.tier1' deployment.json > remediation.json
jq -e --slurpfile policy remediation.json \
  '.remediation = $policy[0] | {settings: .}' current-settings.json \
  > interlay-update.json
eden api request PATCH "/api/v1/interlays/$INTERLAY" \
  --header "Idempotency-Key:$IDEMPOTENCY_KEY" \
  --body-file interlay-update.json --content-type application/json --confirm
```

3. **Verify the serving policy.** Read back the interlay.

```sh
eden api request GET "/api/v1/interlays/$INTERLAY" \
  --header 'X-Eden-Verbose:true'
```

Check that `remediation_status.state` is `ready` and both desired and effective SHA-256 values match the intended declaration. Replay the benign and marked requests in the recorded comparison on an isolated target. Check the recorded response and backend outcome for each probe. Use the request and expected-status table in the linked API example alongside the observed comparison.
4. **Restore the previous policy.** Coordinate the change with any other operator updating this interlay. Read current settings again and merge the saved remediation field into them. If the prior settings had no remediation field, omit it in the replacement. Send the same PATCH with a fresh idempotency key, then read back the intended state. Repeat the verification probes. Keep the affected route isolated if restoring the prior settings reopens exposure.

### Native module `gabriel_sipay_v1`

1. **Prepare the archive.** Use the [version 1.0.0 bundle](../../cve/CVE-2026-85632/README.md) for source, target, and build profile. Configure independent host approval for the installed Eden release. Use the authenticated principals required by the native authority contract. Set `PATCH_ARCHIVE` to the exact schema-2 package and `PACKAGE_SHA256` to its expected archive digest. Verify and import it using the same target interlay.

```sh
printf '%s  %s\n' "$PACKAGE_SHA256" "$PATCH_ARCHIVE" | sha256sum --check &&
  eden api request PUT "/api/v1/interlays/$INTERLAY/patch-packages/$PACKAGE_SHA256" \
    --body-file "$PATCH_ARCHIVE" \
    --content-type application/vnd.eden.patch-package.v2+tar --confirm
```

2. **Approve and activate.** Enroll the publisher key, attest host software inventory, and inspect the configuration returned by import. Obtain independent host approval. Sign the typed statement with the matching SDK. Send the admit action followed by activate for the prepared operation. Use the applicable typed payload for each action in `authority-action.json`.

```sh
eden api request POST "/api/v1/interlays/$INTERLAY/native-authority" \
  --body-file authority-action.json --content-type application/json --confirm
```

3. **Verify the operation.** Read the receipt through the same endpoint. Confirm `serving_now` and the full expected shard acknowledgment. Repeat the report’s benign and marked probes and check the backend observations.
4. **Revoke or restore.** Send revoke with the exact operation UUID. Mandatory protection can refuse traffic until a compatible operation is approved and activated. Verify the restored receipt and repeat the probes.

**Vendor update.** Use the [advisory](https://cve.now/CVE-2026-85632) to select the fixed release for the installed branch. Reported fixed releases include `26.9.1`. Follow the vendor’s update instructions and confirm the version actually loaded by the service.

## Authority lifecycle and negatives

Import 201, `activation: explicit_required`; publisher `enroll_key`, host
`inventory` + `approve`, reader `inspect` refused 403; tampered-statement admit
400; invalid-signature admit 403; `admit` prepared (not serving), `activate`
→ receipt `serving_now`, applied shards **2/2**. Revoke → the identical attack
gets **503** (fail-closed); re-approve + re-activate → 403 again. All recorded
in the evidence JSON.

## Honest scope

The module cannot validate the bearer token itself (no store access at the
gateway), so it enforces presence-of-authorization only — a stolen valid token
still passes, and other status values are unguarded. First live attempt hit the
trailing-slash policy rejection (E04FF) and a native-conditions exact-path
mismatch; both fixed, case re-run clean. Module binary SHA-256 `c77b6260…`,
source [CVE-2026-85632 Rust source](../../cve/CVE-2026-85632/http-request-filter/src/lib.rs).
