# PrestaShop: cross-shop customer records via Webservice API (CVE-2026-71519)

A PrestaShop Webservice API key limited to one shop but allowed to access customers can expose and alter customer records belonging to other shops. An attacker can obtain password hashes or secure keys and change a customer's email or password, giving them control of the account.

**Result.** The marked request reached the synthetic backend and incremented its cross-shop read counter. Both protected configurations returned HTTP 403 with no counter increase. The native module passed the ordinary request and the route-wide policy blocked it.

## The vulnerability

The vendor identifies a missing check on the shop that owns the customer record. The API can authorize the shop named in the request and then load a record from another shop.

## The Eden patch

**Tier 1 — declarative policy.** The recorded rule denies every method on the fixture API route and its descendants. It also blocked the ordinary API probe.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/api",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** The fixture module allows the configured id_shop value of 1 and refuses a different value when it finds the marker in an /api request target.

```rust
const ROUTE: &[u8] = b"/api";
if let Some(pos) = find_ignore_case(target, b"id_shop=") {
    let rest_start = (pos + 8).min(target.len());
    // ...value ends at '&' or ' '; refuse unless it equals the fixture shop value 1
}
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-71519/http-request-filter/api.md).

1. **Prepare the fixture.** Check the installed release against the vendor advisory and use the synthetic backend and test shop values to reproduce the module comparison. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission.
2. **Apply the declaratory policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged.
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the cross-shop request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** Upgrade to 8.2.9 or 9.2.1 for the record-level authorization fix. [PrestaShop advisory](https://github.com/PrestaShop/PrestaShop/security/advisories/GHSA-hjwq-7qvv-qxj4)

## Signed module authority

Import returned HTTP 201 with explicit activation required and signature verification deferred. Read-only inspection was refused (403) for the reader principal, admission of a tampered statement was rejected (400), and admission of an invalid signature was refused (403). The activation receipt reported the module serving on all 32 expected shards. After revocation the advisory-shaped probe received HTTP 503 (fail-closed); re-approval and reactivation restored the refusal.

## Test scope

The fixture compared requests with id_shop=1 and id_shop=2 against a synthetic backend. The source checks the first literal id_shop marker on targets starting with /api and allows the fixture value 1. A request without the marker also passes, and the module does not inspect the selected record, look up the API key's shop associations, or validate duplicate parameters. This test did not exercise PrestaShop's record-level authorization or perform an account takeover.
