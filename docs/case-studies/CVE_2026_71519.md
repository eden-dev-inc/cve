# PrestaShop: cross-shop customer records via Webservice API (CVE-2026-71519)

PrestaShop's Webservice API has a broken access control flaw: the holder of a valid API key restricted to one shop can read and change customer records belonging to other shops in a multi-shop installation. Because the attacker can read password hashes and secure keys and alter a customer's email and password, they can take over those accounts. A multistore deployment's tenant boundary fails wholesale for any key holder.

**Result.** The advisory-shaped request raised the backend counter in the baseline (200, +1): a key scoped to shop 1 read another shop's customer records by overriding the shop scope. The declaratory tier refused it (403, counter unchanged; benign false positive recorded). The native module refused the cross-shop request (403, counter unchanged) while the key's own-shop call stayed HTTP 200 — surgical, verified against an independent backend counter through Eden 1.103.0. This is the sibling of the proven CVE-2026-71531 (cross-shop product access); the same scope-override rule covers both shapes.

## The vulnerability

The Webservice API scopes keys to a single shop but applies caller-supplied shop parameters without checking them, so a restricted key reads and rewrites customer records across the whole multistore installation — including password hashes, secure keys, and the email/password fields that complete an account takeover. Eden fronts the shop's API, so the scope-override request rides an HTTP request Eden can refuse before release.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies every method on the API route family and its descendants. This is a coarse rule: it also blocked the key's own-shop call, which is the recorded false positive — the whole Webservice API goes dark, not just cross-shop access.

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [],
          "path": "/api",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** `gabriel_pscustomer_v1` waits for a complete request, matches the API route, and refuses any request whose `id_shop` parameter names a shop other than the key's own — the scope-override shape the flaw accepts. Requests scoped to the key's own shop continue.

```rust
const ROUTE: &[u8] = b"/api";
if let Some(pos) = find_ignore_case(target, b"id_shop=") {
    let rest_start = (pos + 8).min(target.len());
    // ...value ends at '&' or ' '; refuse unless it equals the key's shop
}
```

## Implement the remediation

The commands are operator examples for the recorded scope. Compare fixture routes and software selectors with the intended deployment before use. See [deployment prerequisites](../deployment.md) and the [API example](../../cve/CVE-2026-71519/http-request-filter/api.md).

1. **Prepare the target.** Verify the loaded PrestaShop version against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission.
2. **Apply the declaratory policy.** Set `INTERLAY` to the target interlay UUID in the authenticated Eden CLI. Save the interlay's complete current settings, place the policy from this report in `settings.remediation`, and PATCH the full settings object with a fresh `Idempotency-Key`. Read the interlay back and confirm `remediation_status.state` is `ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the linked source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and the expected shards are acknowledged.
4. **Verify, revoke, and restore.** Replay the benign and advisory-shaped probes and compare the backend counter. Revoke the operation and confirm the cross-shop request no longer succeeds (fail-closed 503); re-approve, re-admit, and reactivate a replacement operation to restore protection.

**Vendor update.** The fixed release carries the durable repair: the Webservice API must enforce the key's shop scope against caller-supplied shop parameters. Eden's tiers are an enforcement stopgap for a deployment that cannot upgrade immediately.

## Fixture and probes

The benign probe listed customers scoped to the key's own shop (`id_shop=1`). The advisory-shaped probe read another shop's customer records (`id_shop=2`) through the same key. The fixture incremented its marker when a cross-shop scope override reached the API and returned foreign-shop records.

## Measured comparison (2026-11-13 UTC)

The values after each status are the observed increases in the fixture's cross-shop-read counter.

| Probe | Baseline | Declarative policy | Native module |
| --- | --- | --- | --- |
| Benign own-shop API call | 200, 0 | 403, 0 | 200, 0 |
| Advisory-shaped cross-shop override | 200, 1 | 403, 0 | 403, 0 |

The module pins the lab key's authorized shop (shop 1) — an operator must rebuild with their key's own shop, or the SDK must gain configurable scope bindings (a recorded product limitation). Scope overrides reaching legitimately-shared second shops are a bypass to record.
