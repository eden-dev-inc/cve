# pREST `_groupby` SQL injection (CVE-2026-104129)

An unauthenticated remote caller can submit a crafted `_groupby` query parameter to a pREST deployment through 2.3.0 and change the generated SQL's grammar: values containing balanced parentheses take a raw-expression branch gated only by a weak allowlist, allowing an injected `UNION` branch that returns rows from tables the API is not authorized to expose. Update pREST to 2.4.0.

[Vendor advisory](https://github.com/prest/prest/security/advisories/GHSA-v9v2-98xq-627c) · [Module source](modules/CVE-2026-104129.rs)

**Result.** On a real `prest/prest:v2.3.0` container fronting real Postgres, the vendor's published PoC shape reached the product's raw-expression branch and appeared **verbatim in the generated SQL** (observed in the pREST debug log): `SELECT jsonb_agg(s) FROM (SELECT "id" FROM "prest"."public"."public_notes" GROUP BY upper((SELECT version())) UNION SELECT current_user) s`. The vendor PoC shape itself is rejected by Postgres with 42803 (the malformed aggregate) — but the grammar was attacker-controlled. A UNION variant compatible with the outer aggregate then **leaked a row from the non-public `secret_admin` table through the public endpoint** (`[{"id": 22}, {"id": 11}, {"id": 1}]` — the `id: 1` row is `secret_admin`'s, a table the API must not expose). The native module refused both attack shapes with HTTP 403 before release — the crafted `_groupby` never reached the real query builder while the module served — and preserved HTTP 200 for every benign probe, including the plain read, `_groupby=id`, the aggregate form, and the documented `->>having` form. After revocation the interlay failed closed rather than re-exposing the route, and a replacement operation restored the refusal.

## The vulnerability

pREST's 2.3.0 fix for the `_select` parameter (commit e88dabb) routed that field through a strict new gate, `sanitizeSelectField`, but left `_groupby` on the weaker `isSafeSQLExpression` path (`adapters/postgres/postgres.go`, `GroupByClause`). When a `_groupby` value contains balanced parentheses, pREST treats it as a raw SQL expression; the gate checks only the outermost function name against a 13-entry allowlist and permits spaces, quotes and parentheses. It blocks `;`, `--`, `/*`, unbalanced parens and an outer `pg_` prefix — but not a trailing `UNION SELECT ...`, a nested `(SELECT ...)` subquery, or an inner `pg_` function, all three of which `sanitizeSelectField` rejects. `controllers/crud.go:131` calls `GroupByClause` unconditionally and concatenates its output into the executed statement.

The vendor's published PoC:

```
GET /{database}/{schema}/{table}?_select=id&_groupby=upper((SELECT+1))+UNION+SELECT+current_user
```

## Real-product verification (2026-11-19 UTC)

A real `prest/prest:v2.3.0` container (public Docker Hub image) was deployed fronting real Postgres 16 with a public table (`public_notes`, rows `11`/`22`) and a non-public table (`secret_admin`, row `1`) that the API must never expose.

**Vendor PoC, verbatim** — `?_select=id&_groupby=upper((SELECT+version()))+UNION+SELECT+current_user` — the generated SQL in the pREST debug log:

```sql
SELECT jsonb_agg(s) FROM (SELECT "id" FROM "prest"."public"."public_notes"
GROUP BY upper((SELECT version())) UNION SELECT current_user ) s
```

The response is a Postgres 42803 error (the unaggregated `"id"` column) — the injection itself confirmed, with the statement's grammar under attacker control. (Aggregate forms like `max(...)` silently drop the clause — the paren branch is specifically the `upper`-style function-expression path.)

**Exfiltration** — adding the grouped column to satisfy the aggregate (`?_select=id&_groupby=id,+upper((SELECT+version()))+UNION+SELECT+(SELECT+id+FROM+secret_admin)`) produced:

```json
[{"id": 22}, {"id": 11}, {"id": 1}]
```

The `id: 1` row does not exist in `public_notes`; it is `secret_admin`'s row, returned through the public endpoint — a demonstrated read of a table the deployment does not expose. Benign shapes verified on the real product: plain reads, `_groupby=id`, `_groupby=max(id)`, and the documented `->>having:max:id:gt:0` form all behave normally.

## The Eden patch

**Tier 1 — declarative policy.** The recorded policy denies `GET` on the `/prest/public` route family. This is a coarse rule: it also blocks the benign read probes on the same route (recorded false positives).

```json
{
  "version": 1,
  "profile": "http-structure-v1",
  "policy": {
    "version": 1,
    "rules": [
      {
        "scope": {
          "methods": [
            "GET"
          ],
          "path": "/prest/public",
          "descendants": true
        },
        "require": {
          "kind": "deny"
        }
      }
    ]
  }
}
```

**Tier 2 — native Rust module.** The module refuses requests whose `_groupby` parameter (query string or urlencoded body) carries statement grammar beyond a safe grouping expression: after percent-decoding, any quote, semicolon, backtick, NUL/control byte, or character outside the vendor's own fixed-gate charset (`[A-Za-z0-9_().,*->:]`) is injection material — a `UNION` clause cannot be written without whitespace, so a strict per-decoded-byte charset check is the gate. The scan advances a single cursor per parameter source (a second `_groupby` occurrence is found by continuing, never by rescanning). Benign forms pass: bare and qualified columns, aggregates, and the `->>having` operator characters (`:` and `>` are kept safe for it).

```rust
/// Characters a safe `_groupby` expression may carry (the vendor's fixed
/// `sanitizeSelectField`/`ident.Quote` charset, plus commas for multi-field).
fn groupby_safe(b: u8) -> bool {
    // the vendor's fixed gate charset (sanitizeSelectField / ident.Quote):
    // identifiers, separators and the ->>having operator characters.
    // spaces are NOT safe (a UNION clause cannot be written without one).
    b.is_ascii_alphanumeric() || matches!(b, b'_' | b'.' | b'(' | b')' | b',' | b'*' | b'-' | b'>' | b':')
}

/// Stream-decode one `_groupby` value (percent-decoding inline) and decide
/// whether it carries statement grammar beyond a safe grouping expression.
/// A UNION injection always carries whitespace or unsafe punctuation once
/// decoded, so a strict per-decoded-byte charset check is the gate.
fn groupby_is_attack(raw: &[u8]) -> bool {
    let mut i = 0usize;
    let n = raw.len();
    while i < n {
        let b = if raw[i] == b'%' && i + 2 < n && is_hex(raw[i + 1]) && is_hex(raw[i + 2]) {
            let d = (hex_val(raw[i + 1]) << 4) | hex_val(raw[i + 2]);
            i += 3;
            d
        } else {
            let d = raw[i];
            i += 1;
            d
        };
        // quotes, semicolons, NUL and control bytes are statement material
        if matches!(b, b'\'' | b'"' | b';' | b'\x00' | b'\n' | b'\r' | b'`') {
            return true;
        }
        // any character outside the safe grouping-expression charset
        // (spaces included: a UNION clause cannot be written without one)
        if !groupby_safe(b) {
            return true;
        }
    }
    false
}

/// Scan a request's `_groupby` parameters (query string and urlencoded body)
/// for the injection shape. Advances a single cursor per source — a second
/// `_groupby` occurrence is found by continuing the scan, never by
/// rescanning from the start.
fn request_carries_injection(head: &[u8], body: &[u8]) -> bool {
    const KEY: &[u8] = b"_groupby=";
    for src in [head, body] {
        let n = src.len();
        let mut i = 0usize;
        while i + KEY.len() <= n {
            let edge = i == 0 || src[i - 1] == b'&' || src[i - 1] == b'?';
            let eq = edge && {
                let mut m = true;
                for (j, kb) in KEY.iter().enumerate() {
                    if lower(src[i + j]) != lower(*kb) {
                        m = false;
                        break;
                    }
                }
                m
            };
            if eq {
                let start = i + KEY.len();
                let mut end = start;
                while end < n && src[end] != b'&' && src[end] != b' '
                    && src[end] != b'\r' && src[end] != b'\n' {
                    end += 1;
                }
                if groupby_is_attack(&src[start..end]) {
                    return true;
                }
                i = end + 1; // past the terminator
                continue;
            }
            i += 1;
        }
    }
    false
}
```

(Complete module: [modules/CVE-2026-104129.rs](modules/CVE-2026-104129.rs).)

**Stated limits.** String literals inside `_groupby` are refused (no legitimate grouping expression carries a quoted literal after the fixed gate's charset); the module keys on the parameter name, not the route, so it guards every route on a protected deployment. The durable fix is pREST 2.4.0.

## Implement the remediation

1. **Prepare the target.** Confirm the pREST version (`prestd version`) against the advisory. Use a compatible Eden HTTP interlay and an authenticated operator with Configure permission.
2. **Apply the declarative policy.** Set `INTERLAY` to the target interlay UUID. Save the interlay's settings, place the tier-1 policy in `settings.remediation`, and PATCH with a fresh `Idempotency-Key`. Read back `remediation_status.state == ready`.
3. **Import and activate the native module.** Build the schema-2 archive from the published source with the compatible SDK, verify its digest, and PUT it to the interlay's patch-packages endpoint. Import requires explicit activation: enroll the publisher key, attest the host inventory, inspect the returned configuration, obtain independent host approval, sign the typed statement, admit, and activate. Read the receipt until `serving_now` is true and all shards are acknowledged.
4. **Verify, revoke, and restore.** Replay the benign and marked probes and compare the fixture oracle. Revoke and confirm the route fails closed (503); re-approve, re-admit and reactivate a replacement operation to restore protection.

**Vendor update.** The durable fix is pREST 2.4.0 (`_groupby` behind `sanitizeSelectField`).

The fixture is the **real product** (`prest/prest:v2.3.0` container) fronting real Postgres, behind a thin proxy on the qualification network; the proxy's oracle records a `prest_primitive` effect when a response carries a row sourced from the non-public table (detected by the leaked `id: 1` row).

## Environment notes (recorded honestly)

Two lab/product findings from this wave, recorded for the team:

- **Authority inventory rejects slash-containing product names.** A software inventory entry `"product": "prest/prest"` fails the local `native_http_authority inventory` helper with `[E1A03] Remediation error: Remediation policy unavailable`; a slash-free product name passes. The error message does not name the offending field — a validation failure surfaced as an availability error. (Workaround used: product `prest`.)
- **`E05FF` direct-shard retirement loop and interlay-creation dispatch failures.** Bulk-deleting ~900 stale `gabriel-*` interlays whose native module operations had expired (all blocked by `E1A29`) produced a repeating `[E05FF] Connection error: direct-shard retirement failed` background loop, after which interlay creation itself failed with `[E05FF] ... dispatch to shard ... incomplete`. A single-container (serving) restart did not clear it; a full stack restart (authority + application + grpc-collector + serving) did, and the complete lifecycle then recorded cleanly. Likely load- and state-accumulation-related (the host was concurrently running another agent's build at load ~8); worth a look by the runtime team.
